GlitchLab

A glitch synthesizer for pixels. A source runs through an ordered effect stack, modulators move the knobs, a transport clock keeps everything on the grid, and the whole state exports as JSON. This page is the sketch to roast before any code lands in the repo. The rack below is a throwaway spike to test the look and the card contract. It is not repo code.

Gaps and contradictions

  1. Status says spec-complete, but the schemas it depends on (presets, stacks, MIDI maps) don't exist yet. Proposed status: spec-draft until the §4 schemas land.
  2. The effect contract apply(gl, state) hands raw WebGL to every effect. That breaks the dumb-core rule and blocks a WebGPU or recording test backend. §3 proposes plan() instead.
  3. CONTRIBUTING requires effect tests, schema validation and a shader compile gate, but tasks.md has no epic for the harness. §8 adds one and puts it first.
  4. The effects in this spike (stutter, 3D RGB split, granular) aren't in the README list, and they are temporal. The pipeline doesn't model time yet: there's no clock, no frame history and no per-effect state.
  5. Export determinism isn't specified. GIF/MP4 export and golden-image tests both need a seeded, fixed-timestep offline render.
  6. The UI choice "Astro (or vanilla)" is still open (R7).
  7. The links to GlitchWorks and midi-gem were not verified.

§3

Architecture

Dependencies only point down. The core never imports a GL type, effects never touch the GL context, and surfaces never write runtime state directly. They send events, and the core returns snapshots.

LayerOwnsCan seeNever sees
L0Cards: effect cards, stack card, modulators, MIDI map, safety policy, plus their JSON Schemasnothingcode
L1Core, pure TS: registry, transport, modulation, param resolve and clamp, safety policy, FramePlan, exportState/loadState, validation, MIDI parser, clock follower, map resolverL0DOM, GL, wall clock (time is injected)
L2Render backend: GL context, targets, ping-pong, frame history, state targets, context-loss rebuildFramePlan, shader sourcesstack semantics, UI
L3IO: sources (file, camera, URL, test card), sinks (canvas, PNG/WebP, GIF, MP4), offline renderer, MIDI ports (Web MIDI, null, fixture replay, later a native bridge)L1 and L2 interfaceseffect internals
L4Surfaces: rack UI generated from param descriptors, MIDI input, telemetry sinkevents in, snapshots outGL, effect code

Frame tick

  1. 1transport.tick(dt) → t, step, beatpure
  2. 2modulators.sample(t) → bipolar valuespure
  3. 3resolve(stack, routes, mods) → params clamped to their descriptorspure
  4. 4safety.apply(params, policy) → capped params and guard notespure
  5. 5effect.plan(params, ctx) → passes, uniforms, state opspure
  6. 6backend.run(framePlan) → ingest, ping-pong, history ring, state targetsgpu
  7. 7sink.present() or sink.record()io

Steps 1 to 5 produce a FramePlan, which is a plain JSON object. That gives snapshot tests of the whole stack without a GPU, and a backend that only executes plans. The spike runs this exact loop. Its effects are inline JS objects where the real ones would be one module per effect.

// proposed: replaces apply(gl, state) from CONTRIBUTING §2.3
interface EffectModule {
  card: EffectCard;                                   // JSON, validated by schemas/effect-card.schema.json
  plan(p: ResolvedParams, ctx: FrameCtx): EffectPlan; // pure, no GL
}
interface EffectPlan {
  passes: PassSpec[];        // shader ref + uniforms + inputs
  stateOps?: StateOp[];      // e.g. { op: "capture", from: "input", to: "hold" }
}
interface RenderBackend {
  run(plan: FramePlan): void;
  capabilities(): BackendCaps; // max texture, history frames, float targets
  dispose(): void;
}

Card contracts

Params are addressed as <instanceId>.<paramKey>. Instance ids let one effect sit in the stack twice and keep MIDI maps and mod routes stable when the stack is reordered. Descriptor fields: type (number, int, enum, bool), min, max, step, default, curve (linear, exp), flags (e.g. flash-risk), midi.

§5

The four effects in the spike

Stutter gate

temporalflash-risk

The scheduler cuts time into steps of the chosen division, and each step rolls a seeded chance. On a hit the effect captures its input at the step start, holds it for the gate length and re-fires it repeats times. Each repeat is chopped dark for its last ~40%. Later repeats slip sideways with a tear band, like tape catching. A held MIDI note punches it in regardless of chance, like Beat Repeat on a pad.

Params
rate 1/4–1/32 · chance · gate · repeats 1–8 · chop · slip
State
one hold frame per instance
Cost
1 tap per frame, 1 copy per triggered step
Risk
Chop at high retrigger rates is a flash source. The guard caps it.

3D RGB layer split

spatial

Each channel sits on its own depth plane: R behind, G at the screen, B in front. Per plane: perspective scale from depth, keystone from tilt, rotation from twist, and parallax along an axis that orbits on the bar clock. Off-plane pixels go black, so the layer edges show. Plain chromatic aberration is this effect at zero depth and twist.

Params
depth · spread · twist · tilt · orbit · mix
Cost
3 taps
Risk
Low

Granular artifacts

temporal

The frame is cut into square grains. Every reseed tick (a synced division) a seeded hash picks which grains fire. A firing grain samples from an offset position (spray) or from an older frame in the history ring (time spray), and its colour gets crushed. Film grain sits on top.

Params
size 4–64 px · density · spray · time spray · crush · reseed · grain
Cost
1–2 taps
Memory
History is N × W × H × 4 bytes: 16 frames is 59 MB at 720p and 133 MB at 1080p. Needs a cap (§7).

Scanlines / CRT

spatialflash-risk

Barrel curvature, scanlines with roll, an RGB aperture-grille mask, vignette, and per-frame flicker.

Params
lines 60–450 · intensity · roll · curvature · mask · vignette · flicker
Cost
1 tap
Risk
Flicker changes luminance every frame, so the guard caps it.

Not in the spike: pixel sort (needs a GPU multi-pass sort or a CPU worker, so it gets its own spike), displacement, databend, bloom, custom GLSL.

§6

MIDI and Ableton Live

Chrome's Web MIDI gives the page real ports: every MIDI input and output the OS exposes, hot-plug events, and high-resolution event timestamps on the same clock as performance.now(). Outputs also accept a future timestamp, so sends can be scheduled ahead. That's enough to make GlitchLab an instrument inside a Live set. It can follow Live's clock, be played from clips and automation, and send its own knob moves back.

Platform facts that shape the design

Since Chrome 124 every requestMIDIAccess() call sits behind a permission prompt; a refusal throws SecurityError. SysEx is a separate, stronger ask.A "Connect MIDI" button asks on a click, never on load. Refusal leaves the preview running with a clear message. v0 never asks for SysEx.
Firefox needs a site permission too. Safari has no Web MIDI (WebKit bug 107250 is still open).NullMidiPort on Safari: full visuals, MIDI controls disabled with an explanation.

Virtual ports. GlitchLab and Live talk through OS loopback ports. On macOS that's the built-in IAC Driver (Audio MIDI Setup, add buses). Windows and Linux need their own loopback setup; docs/MIDI.md will give per-OS steps once each one is tested. Use three buses: one for sync, one Live → GL, and one GL → Live. Echoing on the same bus you listen on makes a loop.

Timing. Clock math uses each message's event timestamp, never its arrival time. Position is re-anchored on every tick, so tempo estimation can't drift. Video lags audio by a frame or two plus display latency, so midi.offsetMs nudges visuals ahead or behind, like Live's own MIDI Clock Sync Delay.

Safety still applies. MIDI writes base param values, which then go through resolve and the flash guard like everything else. A pad hammering retrig at 1/32 still gets capped. Unmapped messages are ignored, and bursts are coalesced to the latest value per param per frame.

Safety and caps

Concernv0 ruleLater
PhotosensitivityWCAG 2.3.1 puts the line at three flashes per second. The safety policy is a core layer and on by default. If a flash-risk param alternates faster than the policy limit, it is capped (chop to 0.10, flicker to 0.08). Turning the guard off takes an explicit toggle and shows a warning. The spike does this.Measured guard: reduce each output frame to mean luminance (mip or reduction pass, 1×1 readback) and limit frame-to-frame change.

Test harness, before code

Determinism rule: effects never call Math.random. All randomness is hash(seed, frame, cell), and exports and goldens render at a fixed timestep. With that rule, one seed plus one frame index gives one exact image.
